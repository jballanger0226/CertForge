ACME issuing CA

A separate signing key for ACME clients. They renew by themselves, so the key has to be usable without anyone typing a passphrase. Keeping it apart means your main CA can stay locked, and a leak only affects ACME certificates.

Where ACME certificates come from today

ACME clients are signed by your main intermediate CA, {{ main.intermediate.subject }}. That works, but it means the main CA has to stay unlocked whenever a client renews. Pick one of the two ways below to give ACME its own issuing CA.

Signed by your existing root (recommended)

Makes a second intermediate under the root you already have. Every device that trusts your root trusts these certificates straight away, so there is nothing new to install anywhere.

Give ACME its own root (advanced)

For when ACME should be fully separate: its own name, lifetime and key type, or a different owner. It's a new two-level chain with a brand-new root that your main CA has nothing to do with.

Set up a separate root and issuing CA

What this costs you: every device and client that should trust ACME certificates has to install this new root as well as your existing one. The root key is shown to you once, for safekeeping, and by default isn't kept on the server.

Renew

The issuing CA expires on {{ s.issuing.not_after|date }}. Renewing signs it again with the root, with the same name and key, so every certificate it issued keeps working.

{% if (s.mode == 'under-main' and not main.root_key_present) or (s.mode == 'own-root' and not s.root_key_present) %} {% endif %}

Retire

Puts this ACME CA, keys included, into a folder on the server and turns ACME off, so nothing quietly falls back to a different CA. Certificates it issued stay valid until they expire. You can then turn ACME on again with your main CA, or make a new ACME issuing CA.

Retire the ACME issuing CA

Its revocation list stops being updated, so certificates issued by it can no longer be revoked from here.
